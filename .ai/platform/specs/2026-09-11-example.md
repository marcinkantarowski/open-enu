# Example - the reference module

**Status:** accepted · **Date:** 2026-09-11 · **Phase:** 6

## Problem

An agent picking up a task in this repository needs one place to see how a feature is built
here - not nine modules to compare, and not a document describing code that may have moved.
.ai/platform/PLAN.md §12.1 makes that explicit: a feature task must be completable after reading
`AGENTS.md` (routing only) + the target module's `MODULE.md` + **the `Example` module**.

That only works if `Example` shows exactly one of everything and stays cheap to read.
§12.1 budgets it at **800 LOC including tests**, and §6.7 lists what "everything" means:
versioned, tenant-scoped, one encrypted field, one attachment, `attributes` JSONB, list +
create + update, one command and handler, one voter, one `#[ClientBroadcast]` event, one
progress-reporting handler, one flag-guarded route, one `TenantSetupInterface` seed, one
fixture, unit + functional tests run as a user **and** as an API key, a page with i18n, and
a Playwright spec.

`Demo` currently plays this role by accident. It was Phase 2a's proof that discovery works
and Phase 2b's proof that the platform contracts work, and it grew into a second reference
that is near-identical to this one and documented as neither. Two references is the debt
this repository exists to avoid: an agent reads whichever it finds first.

## Approach

Build `Example` to the §6.7 list, then **delete `Demo`** and repoint everything that used it.

One entity, `Project`:

| Concern | How it shows up | Lines |
|---|---|---|
| Tenant scoping | `implements TenantScopedInterface` | 1 |
| Optimistic locking | `implements VersionedInterface` + `#[ORM\Version]` | 2 |
| Field encryption | `#[ORM\Column(type: EncryptedTenantStringType::NAME)]` | 1 |
| Open-ended data | `attributes` JSONB (ADR-0013, instead of custom fields) | 2 |
| Attachment | a plain `attachmentId` uuid, set from the upload | 1 |

That table is the argument for the module: every cross-cutting concern is an attribute or a
one-liner, which is what a reader is meant to take away.

Three write paths, each demonstrating a different thing:

- `POST /api/projects` - command + handler + `ProjectCreated` (`#[ClientBroadcast]`)
- `PATCH /api/projects/{id}` - `If-Match`, so the 409 path is exercised; also carries the
  module's one `#[DeniedUnderImpersonation]`
- `POST /api/projects/archive` - `#[Flag('example.archive')]` and a progress-reporting
  handler, so the kill switch and the long-job pattern both have a live example

One record-level voter (`ProjectVoter`) on top of the permission voter: permissions say what
a *role* may do, the voter says whether *this row* may be touched. Both, because the two
answer different questions and the repository has no example of the second.

### A gap this surfaced: nothing could declare a flag

`#[Flag('example.archive')]` resolves through `PersistentFlags` → a `Setting` row → the
attribute's default. **Nothing in the repository creates a `Setting` row.** The manager's
flags page listed nothing, `GET /api/settings` returned an empty array, and `demo.archive`
could never be switched on - Phase 4 shipped the resolution chain without the declaration
step, and no test noticed because no test needed a flag to be *on*.

Phase 6 cannot meet its own acceptance criteria without it ("archive shows progress" needs
the flag on; "flag off → 404" needs it off), so this phase closes the gap:

- **kernel** - `Flags/FlagDefinition` + `Flags/FlagProviderInterface`, autoconfigured onto
  `open_enu.flag_provider`. The kernel owns the *contract*, as it does for every other
  platform service, so a module declaring a flag depends on the kernel and not on Settings.
- **Settings** - collects the tagged providers and reconciles them into `Setting` rows via
  `app:flags:sync`, which is idempotent and never touches a tenant's overrides.
- **Example** - declares `example.archive`, which is what makes it demonstrable.

## Rejected

- **Keeping `Demo` alongside `Example`.** Two reference modules means an agent reads the
  wrong one; `Demo`'s own `MODULE.md` already said to delete it once real modules arrived.
- **Declaring settings in `module.yaml`.** A setting has a type, a default, a category and a
  `tenantEditable` flag; expressing that in the manifest makes the manifest a schema.
- **A `SettingProviderInterface` owned by the Settings module.** It works, but then every
  module that wants a flag gains `depends: [Settings]`. The kernel already owns
  `FlagsInterface` and `#[Flag]`; the declaration belongs with them, exactly as
  `TenantSetupInterface` is a kernel contract that the Tenant module runs.
- **Creating `Setting` rows from a migration.** Migrations belong to schema, not to content,
  and a flag added by a module three months from now would need a migration in another
  module to become visible.
- **A search index on `Project`.** .ai/platform/PLAN.md gives that to Phase 7; adding it here would make
  this module the place two phases meet.

## Surface

- API: `GET /api/projects`, `POST /api/projects`, `GET /api/projects/{id}`,
  `PATCH /api/projects/{id}`, `POST /api/projects/archive`
- UI: `/example`
- Permissions: `example.view`, `example.manage`
- Events: `example.project.created` (`#[ClientBroadcast]`)
- Flags: `example.archive` (default off)

## Tests that ship with it

- [x] Unit: the archive handler reports progress and stops at the first failure
- [x] Functional: every route, as a user **and** as an API key; stale `If-Match` → 409;
      flag off → 404; impersonated PATCH → 403
- [x] E2E: create → the list updates live, **and tenant B's stream receives nothing**;
      stale update → conflict bar; archive → progress; flag off → the action reports
      unavailable
