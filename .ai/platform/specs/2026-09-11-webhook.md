# Webhook - outbound events, signed and retried

**Status:** accepted · **Date:** 2026-09-11 · **Phase:** 7

## Problem

Every event this system raises is currently visible in exactly two places: a browser with an
open connection, and the audit log. Anything a customer wants to *build* on - sync to their
CRM, post to Slack, kick off their own pipeline - has to poll, and polling an API for
changes is the integration of last resort.

## Approach

Per-tenant endpoints subscribed to event names, with the delivery log as the product rather
than as a debugging aid: "did you send it?" is the only question anyone asks about webhooks,
and answering it after the fact needs the payload, the response code and the attempt count
kept.

`WebhookPublisher` subscribes to `DomainEvent` **itself**, not to named events, so a module
that adds an event gets webhooks with no change in either place. Subscription lives in the
tenant's endpoint row.

Signing is [Standard Webhooks](https://standardwebhooks.com): `webhook-id`,
`webhook-timestamp`, `webhook-signature: v1,<base64 HMAC-SHA256>` over
`{id}.{timestamp}.{payload}`. A published scheme, because the receiver is somebody else's
code and should be able to verify with an off-the-shelf library.

Retries are Messenger's: the handler throws, and the `jobs` transport's `retry_strategy`
(5 attempts, exponential) does the backoff. A second retry mechanism beside the real one is
how two of them end up disagreeing.

### The thing that was not obvious

**A handler cannot record its own failure.** Every handler runs inside `doctrine_transaction`,
so a row written before a throw is rolled back with it - the log read `attempts: 0` while the
worker logged five retries. `Listener\RecordFailedDeliveryListener` writes the attempt after
that rollback, which is the only correct place for it. See
[[a-handler-cannot-record-its-own-failure]].

## Rejected

- **Inbound webhooks.** Receiving someone else's events is a per-provider problem -
  signature scheme, replay window, payload shape - and a generic inbound endpoint is a
  generic security hole. `InboundAdapterInterface` when a specific provider is needed.
- **Deleting endpoints.** The delivery log points at them, and "which URL did we send that
  to?" is what an incident asks. Deactivated instead.
- **Letting the tenant choose the signing secret.** A secret somebody chose is one they may
  have chosen badly, or reused from somewhere else.
- **`GET /api/events` listing every event the system can emit.** That is a map of the
  application's internals handed to anyone with a login. The frontend lists the subscribable
  names it knows about.
- **Plain `http://` endpoints.** The payload is signed, not encrypted; plain HTTP publishes
  every event to anyone on the path. The local receiver runs behind Traefik with TLS rather
  than carving an exception into the rule.

## Surface

- API: `GET|POST /api/webhooks`, `DELETE /api/webhooks/{id}`,
  `GET /api/webhooks/deliveries`, `POST /api/webhooks/deliveries/{id}/redeliver`
- UI: `/settings/webhooks`
- Permissions: `webhook.view`, `webhook.manage`
- Notifications raised: `webhook.delivery_failed` (feed + email)

## Tests that ship with it

- [x] Unit: the signature matches the published spec, computed independently; all three
      signed components change it; a stale timestamp is refused
- [x] Functional: a subscribed event becomes a signed request a receiver can verify; a
      failing receiver is retried and each attempt appears in the log; an unsubscribed event
      and a deactivated endpoint both produce nothing
- [x] Live: verified against a real receiver over TLS in the dev stack, with the signature
      checked by an independent HMAC
