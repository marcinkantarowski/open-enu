# Internationalisation

Two locales from day one - `en` and `pl` - so that adding a third is a file rather than a
project. [ADR-0020](../adr/0020-i18n-from-the-start.md) explains why retrofitting this is
the expensive option.

**Never hard-code a user-facing string.** Every one goes through a key, on both sides. The
parity check (`make i18n-check`, in `make check`) fails when a key exists in one locale and
not the other, because the symptom otherwise is a raw key rendered in production, to
exactly the users who read that language.

---

## Where catalogues live

| Side | Path | Shape |
|---|---|---|
| Backend | `backend/src/Module/<Name>/i18n/messages.{en,pl}.json` | Symfony's `<domain>.<locale>.json` |
| Frontend | `<layer>/i18n/locales/{en,pl}.json` (+ `.ts`) | Nuxt's `<locale>.json` |

Each convention is native to its own side rather than unified - the discovery in both cases
is somebody else's, and fighting it costs more than the asymmetry does. Module catalogues
are discovered from the directory: no central file registers one.

### The `.ts` wrapper, and why it exists

```ts
// ui-kit/i18n/locales/en.ts
import messages from './en.json'

export default messages
```

`@nuxtjs/i18n` is pointed at the `.ts`, never the `.json`. Registering the JSON directly
makes Vite's json plugin wrap the output of the i18n transform in `JSON.parse()`, and the
landing site - the one app that renders on the server - dies at boot with
`Unexpected token 'c', "const reso"`. The data stays in the `.json` so the parity check can
read it; the loader points at the wrapper.

Do not set `langDir`. `@nuxtjs/i18n` already resolves `<layer>/i18n/locales`, and overriding
it produces `i18n/i18n/en.json` - a path that silently matches nothing.

## Frontend

```vue
<template>
  <h1>{{ $t('example.projects.title') }}</h1>
  <p>{{ $t('example.projects.count', { n: projects.length }) }}</p>
</template>
```

A module layer contributes its own catalogue next to its own pages, and `@nuxtjs/i18n`
merges the `files` arrays across layers. Keys are namespaced by module for that reason: two
layers contributing `title` would be one merge away from an argument.

Locale detection uses a cookie (`open_enu_locale`) with `SameSite=Lax`, not `Strict`: the
landing site links into the app across subdomains, and a strict cookie is dropped on exactly
that navigation, resetting the language every time somebody signs in.

## Backend

```php
$this->translator->trans('identity.email.verify.subject', [], 'messages', $locale);
```

The locale for a response is resolved by the kernel's `LocaleResolver`, which asks, in
order:

1. every `LocalePreferenceProviderInterface` - Identity contributes the signed-in user's
   saved preference;
2. `Accept-Language`, narrowed to the locales that actually ship;
3. the tenant's default;
4. `en`.

A module influences that by implementing the interface, never by reading a header itself.

### Things that are written once and read later

A notification row stores a **type and arguments**, never a sentence:

```php
$this->notifier->toTenant($tenantId, WebhookNotifications::DELIVERY_FAILED, [
    'event' => $delivery->eventName(),
    'attempts' => $delivery->attempts(),
]);
```

The declaration carries `titleKey` and `bodyKey`; the feed endpoint returns those keys and
the client translates them in the reader's language. Storing prose would freeze the message
in whatever language the worker happened to be running in - which is usually the language of
nobody who will read it.

The same rule applies to emails (rendered at send time, in the recipient's locale) and to
anything queued.

## Adding a locale

1. Add `{ code: 'de', language: 'de-DE', files: ['de.ts'] }` to `ui-kit/nuxt.config.ts`.
2. For every layer and every backend module, copy `en.json` → `de.json` and add the `.ts`
   wrapper.
3. Add `de` to `UpdateProfileHandler::LOCALES`, or the profile endpoint will refuse it -
   deliberately, because a setting that "saves" and then does not apply is a bug report
   nobody can reproduce.
4. `make i18n-check` tells you exactly which keys are missing.
